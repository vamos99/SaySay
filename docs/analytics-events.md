# Product Analytics Event Schema

This document defines the first analytics contract for SaySay game flows. It is
documentation only; no database migration or live event write is included in
this pass.

## Goals

- Make game activity measurable without tying the dashboard to ad hoc fields.
- Keep parent-facing KPIs explainable: weekly activity, completion, accuracy,
  and response time.
- Avoid storing direct personal contact data in analytics events.

## Common Fields

| Field | Type | Required | Notes |
| --- | --- | --- | --- |
| `event_id` | string | yes | UUID generated by client or backend |
| `event_name` | string | yes | One of the event names below |
| `occurred_at` | ISO timestamp | yes | Client event time; backend may add received time later |
| `session_id` | string | yes | Game session UUID |
| `child_id` | string | yes | Supabase child id; no direct child name in event payload |
| `game_id` | string | yes | Example: `oyun1`, `oyun2`, `oyun3` |
| `difficulty` | string | no | Example: `short`, `medium`, `long` |
| `theme` | string | no | Child/game theme at event time |
| `metadata` | object | no | Small event-specific fields only |

## Event Names

| Event | When | Key Metadata |
| --- | --- | --- |
| `game_session_started` | Child starts a game flow | `source`, `selected_child_present` |
| `question_viewed` | A question is displayed | `question_id`, `question_index` |
| `answer_submitted` | Child submits or selects an answer | `question_id`, `is_correct`, `response_time_ms` |
| `tts_played` | TTS starts for a prompt/question | `question_id`, `text_length` |
| `game_session_completed` | Game ends normally | `question_count`, `correct_count`, `duration_ms` |
| `content_generated` | AI content is generated or reused | `concept`, `from_cache`, `from_db`, `model` |

## Parent Dashboard KPIs

| KPI | Definition |
| --- | --- |
| Weekly active sessions | Count of `game_session_started` in the selected week |
| Completion rate | Completed sessions divided by started sessions |
| Accuracy rate | Correct `answer_submitted` events divided by answered events |
| Median response time | Median `response_time_ms` for answer events |
| AI reuse rate | `content_generated.from_db=true` or `from_cache=true` share |

## Implementation Notes

- Keep event writes resilient: gameplay should continue if analytics logging
  fails.
- Do not include child names, emails, payment data, or prompt secrets in event
  payloads.
- Prefer batched writes or low-priority async calls when this is implemented.
